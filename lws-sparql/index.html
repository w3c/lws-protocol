This document extends the Linked Web Storage (LWS) protocol with an optional server-managed SPARQL Query Service that evaluates SPARQL queries over the RDF content of a storage. Queries are conveyed with the HTTP QUERY method, whose safe, idempotent, and cacheable semantics let the query travel in the request content rather than the request URI. The specification defines how the service is discovered, the RDF dataset a query is evaluated against, the request and response formats and their error handling, and the authorization requirements that keep every result client-specific.

This is an unofficial proposal. It is not part of the Linked Web Storage Protocol 1.0 suite: implementing it is entirely optional, and a conforming LWS server need not support it.

Introduction

The [[!LWS10-CORE|Linked Web Storage]] protocol defines a resource-centric storage system built on HTTP: clients create, read, update, and delete resources, and containers enumerate the resources they contain. Much of what a storage holds is RDF, yet the core protocol offers no way to ask questions that span resources. The Type Search Service of [[LWS10-INDEX]] takes a first, deliberately bounded step — a conjunctive filter over resource types and indexed link relations — and caps its own expressiveness there, delegating anything richer to an alternate query format identified by its own media type.

Some applications need that richer step: joins across resources, graph pattern matching, property paths, value filtering, aggregation — in short, SPARQL [[!sparql11-query]]. The SPARQL Protocol [[sparql11-protocol]] binds query evaluation to GET, carrying the query percent-encoded in the request URI — subject to request-URI length limits and to exposure in URI-based logs — or to POST, which is neither safe nor idempotent nor cacheable as far as generic HTTP components can know, so that an intermediary can neither retry nor cache it. The HTTP QUERY method [[!RFC10008]] resolves exactly this tension: a method that is safe, idempotent, and cacheable, whose request content carries the query.

This specification binds SPARQL query evaluation to the QUERY method for LWS storages. It defines a server-managed SPARQL Query Service, discoverable via the storage description resource like the other LWS services; the queryable dataset a query is evaluated against, derived from the storage's resources and filtered by the requesting agent's authorization; and the request formats, response formats, and error handling of the query operation. The service is an optional extension for deployments that want graph-level query capability; [[!LWS10-CORE]] already provides that a storage description may reference additional services whose APIs are defined outside the core specification, and the SPARQL Query Service is such a service.

Relationship to the Type Search Service

The Type Search Service and the SPARQL Query Service are complements, not competitors. The Type Search filter is the bounded-cost baseline: its grammar is frozen, its evaluation cost is predictable, and a portable client can rely on it. SPARQL is the opt-in power tool: every Type Search type filter is expressible as a SPARQL basic graph pattern over the same storage, while the reverse does not hold — and the extra expressiveness is correspondingly more expensive to evaluate and to guard. [[LWS10-INDEX]] anticipates exactly this split when it states that richer expressiveness is offered only through an alternate query format identified by its own media type; application/sparql-query is such a format, here given a service of its own. A server implementing both may even serve both from one endpoint (see ).

Terminology

The terms "storage", "storage root", "storage description resource", "Storage Resource", "container", "containment", "data resource", "auxiliary resource", "resource manager", and "requesting agent" are defined by [[!LWS10-CORE]]. The term "Type Search Service" is defined by [[LWS10-INDEX]]. The terms "RDF graph", "RDF dataset", "named graph", "default graph", and "blank node" are used as defined by [[!rdf11-concepts]].

This specification defines the following additional terms:

  • SPARQL Query Service — a server-managed service, identified by the SparqlQueryService service type, that evaluates SPARQL queries [[!sparql11-query]] over the queryable dataset of a storage as visible to the requesting client.
  • queryable dataset — the RDF dataset a query is evaluated against: one named graph per RDF-bearing resource the requesting agent is authorized to read, each named by the resource's URI, with the union of those graphs as the default graph. Defined in .
  • RDF-bearing resource — a data resource whose representation the server can parse as an RDF concrete syntax (see ).

Discovery

A storage MAY support the SPARQL Query Service. A storage that supports it MUST advertise it with a service object in the service array of its storage description resource whose type equals SparqlQueryService. The service object MUST include a serviceEndpoint property whose value is the URI of the query endpoint. Additional properties MAY be present on the service object. 

{
  "@context": [
    "https://www.w3.org/ns/cid/v1",
    "https://www.w3.org/ns/lws/v1"
  ],
  "id": "https://example.org/storage/alice/",
  "type": "Storage",
  "service": [
    {
      "type": "StorageRoot",
      "serviceEndpoint": "https://example.org/data/"
    },
    {
      "type": "TypeSearchService",
      "serviceEndpoint": "https://example.org/types/search"
    },
    {
      "type": "SparqlQueryService",
      "serviceEndpoint": "https://example.org/sparql"
    }
  ]
}

The service endpoint may be the same URI as another QUERY-accepting endpoint of the storage — for example the Type Search Service of [[LWS10-INDEX]] — since [[RFC10008]] distinguishes query formats by the request's Content-Type header field, and Accept-Query can advertise both (for example Accept-Query: application/lws-query+json, application/sparql-query). Requests in each format are governed by that format's specification.

Service Description

A GET request to the service endpoint SHOULD return a SPARQL service description [[sparql11-service-description]], subject to ordinary content negotiation (for example as text/turtle or application/ld+json). The description SHOULD state the query language versions the service supports (sd:supportedLanguage), SHOULD assert sd:feature sd:UnionDefaultGraph — the default-graph behavior required by — and MAY enumerate supported result formats (sd:resultFormat).

A service description is computed for the requesting agent like every other response of the service: it MUST NOT enumerate named graphs, counts, or dataset statistics beyond the agent's authorized view (see ).

The Queryable Dataset

Every request is evaluated against a queryable dataset: an RDF dataset [[!rdf11-concepts]] derived from the storage and filtered by the requesting agent's current authorization. The queryable dataset is constructed as follows:

  • For each data resource in the storage that the requesting agent is authorized to read and that is an RDF-bearing resource, the dataset contains one named graph. The graph name is the resource's URI — the same URI by which the resource is identified for the operations of [[!LWS10-CORE]] — and the graph is the RDF graph expressed by the resource's representation.
  • The default graph is the union of the graphs of all named graphs in the queryable dataset. A blank node in the default graph is the same blank node as in the named graph it originates from, and blank nodes contributed by different resources are always distinct.
  • A server MAY additionally include server-managed graphs — for example, a named graph for a container, named by the container's URI and containing the RDF expressed by its container representation (containment and membership metadata), or a named graph for an auxiliary resource such as a metadata resource. Server-managed graphs are subject to the same authorization filtering as every other graph and, when present, contribute to the default graph like any other named graph.

An RDF-bearing resource is a data resource whose representation the server can parse as an RDF concrete syntax. A server implementing this service MUST treat representations served as text/turtle [[!turtle]] and as application/ld+json [[!json-ld11]] — including the application/lws+json profile defined by [[!LWS10-CORE]] — as RDF-bearing, and MAY treat additional RDF serializations (for example application/n-triples or application/rdf+xml) as RDF-bearing. A resource that is not RDF-bearing contributes no graph to the dataset, and a representation that fails to parse likewise contributes no graph; neither case is an error for a query — the resource's data is simply absent from the dataset.

An IRI carrying a fragment identifier, such as https://example.org/data/people/person-4872#me, denotes something described by the document at the fragmentless URI; triples about it therefore occur in the named graph named by that document URI.

The queryable dataset MAY be eventually consistent with respect to writes. Following a write that changes a resource's contribution to the dataset (creation, update, or deletion), a server SHOULD reflect the change within a bounded, implementation-defined interval; until it does, a query MAY fail to observe a recent write or MAY briefly observe data that has since been removed. Clients MUST NOT assume read-your-writes consistency and SHOULD tolerate transient staleness. This allowance applies only to dataset derivation and MUST NOT be applied to authorization filtering (see ).

A server will typically maintain a materialized index — for example, a quad store mirroring the storage — rather than parsing resources at query time. Such an index is an implementation detail: the observable dataset is the one defined here, and the authorization requirements of apply to every response regardless of how the dataset is materialized.

Dataset Clauses (FROM, FROM NAMED)

A query MAY carry dataset clauses (FROM, FROM NAMED) [[!sparql11-query]]. Dataset clauses select from the queryable dataset; they never extend it. A FROM or FROM NAMED IRI that equals the graph name of a graph in the queryable dataset selects that graph. Any other IRI — one identifying a resource the requesting agent is not authorized to read, a resource that is not RDF-bearing, a resource that does not exist, or a URI outside the storage entirely — MUST be treated as naming an empty graph, and these cases MUST be indistinguishable from one another in every observable aspect of the response. A server MUST NOT dereference an IRI in order to construct a graph for a dataset clause.

Treating out-of-scope and unauthorized graph IRIs identically to empty graphs keeps dataset clauses from serving as an oracle for the existence of resources the client cannot read; see .

Federated Query (SERVICE)

The SERVICE clause of federated query [[sparql11-federated-query]] instructs a query processor to contact a remote endpoint during evaluation. A server MUST NOT evaluate SERVICE clauses unless it has been explicitly configured to do so; in the absence of such configuration, a query containing a SERVICE clause — SILENT or not — MUST be rejected with 422 (Unprocessable Content) (see ). A server that does evaluate SERVICE clauses MUST NOT forward the requesting agent's credentials to the remote endpoint and SHOULD restrict the set of endpoints it will contact; see .

SPARQL Query Operation

QUERY [SparqlQueryService]

A client queries by sending an HTTP QUERY request [[!RFC10008]] to the service endpoint, carrying the SPARQL query in the request content. The query format is identified by the request's Content-Type header field, which MUST be present; per [[!RFC10008]], a server fails the request if the Content-Type is missing or inconsistent with the content (see ). Every server MUST support the application/sparql-query format [[!sparql11-protocol]], whose content is a single query string in the SPARQL query language [[!sparql11-query]], encoded in UTF-8; a server MAY additionally accept other query formats, each identified by its own media type, and the authorization requirements of apply regardless of the format used. The QUERY method is both safe and idempotent [[!RFC10008]], in the sense of those terms as defined by [[!RFC9110]]: a SPARQL query never alters server state, and it MAY be repeated, retried, and/or cached. Because the query travels in the request content rather than the request URI, it is not subject to the request-URI length limits that constrain the query-string binding of the SPARQL Protocol [[sparql11-protocol]].

This binding defines no URI query parameters. In particular, the SPARQL Protocol parameters default-graph-uri and named-graph-uri are not used: the dataset a query is evaluated against is the queryable dataset (), possibly restricted by dataset clauses inside the query itself (). A client requests the advertised serviceEndpoint URI as-is.

The SPARQL query language defines four query forms [[!sparql11-query]]. A server MUST support the SELECT, ASK, and CONSTRUCT forms. A server SHOULD support the DESCRIBE form; because the content of a DESCRIBE result is implementation-defined by [[!sparql11-query]], a server MAY instead decline it, and a server that does not support a query form MUST reject a query using it with 422 (Unprocessable Content) (see ).

SPARQL update operations are outside the scope of this specification. The SPARQL update language is a distinct language with its own media type, and a request carrying application/sparql-update MUST be rejected with 415 (Unsupported Media Type): the QUERY method is safe, and a server MUST NOT execute any state-changing operation in response to it [[!RFC10008]].

The baseline query language is SPARQL 1.1 Query [[!sparql11-query]]. A server MAY implement a later version of SPARQL; it SHOULD advertise the language versions it supports in its service description (see ), and a portable client MUST NOT rely on language features beyond SPARQL 1.1 unless it has confirmed their support there.

A server SHOULD advertise the query formats it accepts using the Accept-Query response header field [[!RFC10008]] — for example in response to an OPTIONS request on the service endpoint, whose Allow header also signals that the QUERY method is supported. The Accept-Query value MUST include application/sparql-query. Accept-Query enumerates only query-format media types; it says nothing about the language features, query forms, or dataset contents the service supports. A client that receives a 415 (Unsupported Media Type) response MAY consult its Accept-Query value to select a supported format.

The QUERY method is not a safelisted method for cross-origin requests, so browser-based clients trigger a CORS preflight (OPTIONS) before sending it [[RFC10008]]. A server intended for use by browser-based LWS clients therefore needs to answer preflight requests for the service endpoint appropriately.

Responses

A successful query returns 200 (OK), whatever the size of the result: an empty solution sequence, an empty graph, and an ASK result of false are all successful results. The response media type is determined by the query form and the request's Accept header field:

  • For SELECT and ASK, every server MUST be able to produce application/sparql-results+json [[!sparql11-results-json]], and MAY offer additional result formats such as application/sparql-results+xml, text/csv, or text/tab-separated-values [[sparql11-results-csv-tsv]].
  • For CONSTRUCT and DESCRIBE, every server MUST be able to produce text/turtle [[!turtle]], and MAY offer additional RDF serializations such as application/ld+json [[json-ld11]] or application/n-triples.

A request that sends no Accept header field, or one that admits the mandatory format for its query form, receives that format. A server MAY honor an Accept header field requesting a different media type and return the result in that format instead [[!RFC10008]]; if it can satisfy none of the media types the request finds acceptable, it responds 406 (Not Acceptable) (see ).

This specification defines no pagination for query results: the LWS pagination model of [[!LWS10-CORE]] does not apply to the SPARQL Query Service. Clients page through large result sets with the solution modifiers of the query language itself — ORDER BY, LIMIT, and OFFSET [[!sparql11-query]] — which is also the approach [[!RFC10008]] recommends in preference to HTTP range requests. This specification defines no range-request handling for query results.

OFFSET-based paging is only as stable as the dataset underneath it; a concurrent write can shift solutions between pages. Clients that need a stable enumeration should impose a total order with ORDER BY.

A server MAY bound the resources a query is allowed to consume — execution time, memory, or result size. A server that cannot complete a query within its bounds MUST fail the request (see ); it MUST NOT return a truncated result presented as complete.

A server MAY implement conditional QUERY requests: per [[!RFC10008]], the selected representation of a QUERY is the same as for a GET of the equivalent resource, so a server MAY emit a validator (such as an ETag) with a query response and honor conditional header fields such as If-None-Match on a repeated query. Any such validator MUST be scoped to the requesting agent's authorized view, in line with .

Errors

Servers indicate request outcomes using standard HTTP status codes [[!RFC9110]]. In particular:

  • Request content that is not a syntactically valid SPARQL query [[!sparql11-query]] MUST be rejected with 400 (Bad Request). A SPARQL update string is not a valid query — the update language is a separate grammar — so an update submitted as application/sparql-query is likewise rejected with 400.
  • A request that omits the Content-Type header field, which [[!RFC10008]] requires a server to reject, MUST be rejected with 400 (Bad Request), as MUST a request whose Content-Type is inconsistent with its content.
  • A request whose Content-Type identifies a query format the server does not support MUST be rejected with 415 (Unsupported Media Type), and such a response SHOULD include an Accept-Query header field [[!RFC10008]] listing the query formats the server does accept; every server supports at least application/sparql-query (see ). A request carrying application/sparql-update is always rejected this way.
  • A request whose Accept header field excludes every response media type the server can produce for the query's form MUST be rejected with 406 (Not Acceptable) [[!RFC10008]]. Because every server can produce application/sparql-results+json for SELECT and ASK and text/turtle for CONSTRUCT and DESCRIBE, a request that omits Accept, or admits the mandatory format for its form, never results in 406.
  • A query that is syntactically valid but that the server declines or fails to process MUST be rejected with 422 (Unprocessable Content), the status [[!RFC9110]] defines and [[!RFC10008]] suggests for a query that is understood but cannot be processed due to its actual contents. This includes a query form the server does not support (see ), a SERVICE clause the server will not evaluate (see ), a query exceeding the complexity the server chooses to support, and a query whose evaluation exceeded the server's execution-time or result-size bounds. A server MUST NOT silently truncate a result set or otherwise narrow a query, as doing so would misrepresent the result as complete.
  • Referencing data the requesting agent is not authorized to read is never an error: such data is simply absent from the queryable dataset, and every observable aspect of the response MUST be indistinguishable from the data not existing (see and ).

Error responses may include a representation describing the problem — for example, a parser diagnostic; this specification does not define its format. applies to diagnostics as it does to results.

Caching

A QUERY response is cacheable [[!RFC10008]]. Because the query travels in the request content, it forms part of the cache key itself ([[!RFC10008]], Section 2.7) and cannot be conveyed through the Vary header field, which names only request header fields. A server that negotiates the response representation on Accept (see ) MUST list Accept in Vary so that caches do not reuse a representation across response formats. Because every result is evaluated against an authorization-filtered dataset and is therefore client-specific, the cross-client caching requirements in also apply.

[[!RFC10008]] permits a cache to normalize request content when computing the cache key — for a SPARQL query, for example, by collapsing insignificant whitespace or comments. Normalization affects only cache-key computation, never the request itself, and an incorrect normalization risks serving one query's results for another; a cache without specific knowledge of the application/sparql-query media type is safest treating the content byte-for-byte.

Equivalent Resources and Result Resources

[[!RFC10008]] allows a response to identify related resources: a Content-Location header field naming a resource that represents the results of the query, and a Location header field naming an equivalent resource from which the same query's results can later be retrieved with GET. Because every result set is authorization-filtered and client-specific (see ), this specification does not define such resources. A server that nonetheless exposes one MUST subject every access to it to the same authorization filtering, MUST prevent its reuse across clients, and SHOULD ensure its URI embeds no sensitive portion of the query [[!RFC10008]].

Resource-Scoped Queries

The service endpoint of evaluates queries against the whole storage. A server MAY additionally accept QUERY requests carrying application/sparql-query directly on Storage Resources, scoping the dataset to the request target:

  • on the storage root, with the same queryable dataset as the service endpoint;
  • on a container, with the queryable dataset restricted to the graph of the container itself (where the server includes container graphs) and the graphs of every resource transitively contained by it;
  • on a data resource, with the queryable dataset restricted to that resource's graph.

In every case the restricted dataset is derived and authorization-filtered exactly as in — the default graph is the union of the graphs remaining in scope — and all other requirements of this specification apply unchanged. A target that is not RDF-bearing yields an empty dataset; a query over it succeeds with an empty result. Access to the target resource itself is governed by [[!LWS10-CORE]]: a request whose target the requesting agent is not permitted to read fails as any read of that resource would, before any query evaluation.

Support for resource-scoped queries is OPTIONAL and per-resource. A server advertises it as [[!RFC10008]] provides: by including QUERY in the Allow header field of responses to the resource (for example to OPTIONS) and by the Accept-Query response header field. A QUERY request on a resource for which the server does not implement this section fails as any unsupported method does — 405 (Method Not Allowed) with an Allow header field, per [[!RFC9110]].

Resource-scoped queries give SPARQL the target-scoping the QUERY method natively has — "a query over the data reachable from this resource" — without minting per-scope endpoints, and compose naturally with the LWS containment hierarchy.

Security and Authorization

Servers MUST enforce authorization. The queryable dataset from which every response is computed contains only the content of resources the requesting agent is authorized to read (see ), and this holds equally for the service endpoint and for resource-scoped queries.

Unauthorized data MUST be omitted entirely. A server MUST NOT allow a client to learn, from any observable aspect of the service's responses — solutions, constructed triples, graph names enumerated through a GRAPH variable, boolean ASK results, error responses, or diagnostics — the existence of a specific resource, graph, or triple, or that a specific term occurs in the storage at all, without the required authorization. This implicit filtering yields a dynamically evaluated, client-specific view of the storage.

Every value a response exposes, including every aggregate (such as COUNT, SUM, or GROUP_CONCAT), MUST be computed over this client-specific, authorization-filtered dataset: an aggregate is the value over the data the requesting agent is authorized to see, never over the storage as a whole. A value that reflected unauthorized data would itself reveal that data's existence and is therefore prohibited.

Authorization filtering MUST be evaluated against the requesting agent's current access at the time the request is served, not against any cached or precomputed view. Once an authorization (such as an access grant) is revoked or narrowed, the affected graphs and triples MUST NOT contribute to any subsequent response; the eventual-consistency allowance for dataset derivation (see ) MUST NOT be extended to authorization. A server MAY maintain a materialized dataset or index for performance, but it MUST apply current authorization as a filter over it on every request.

Responses are authorization-filtered and therefore client-specific, yet cacheable by default per [[!RFC10008]], whose cache key is computed over the request content rather than the requesting client. A server MUST ensure that an authorization-filtered response is never served from a shared cache to a different client. A server MUST mark such responses so that they are not reused across clients (for example with Cache-Control: private or no-store) and MUST vary any cached entry on the credential that scopes the result.

Any additional query format a server accepts at the service endpoint, and any other query surface it exposes over the storage, MUST uphold these requirements, so that no query mechanism can become a discovery oracle for resources or data the client is not authorized to read. This is the same requirement [[LWS10-INDEX]] places on extension query mechanisms; a SPARQL Query Service deployed alongside a Type Search Service satisfies it by conforming to this section.

Security Considerations

  • Resource Exhaustion: SPARQL is far more expressive than the baseline Type Search filter of [[LWS10-INDEX]], and adversarial or merely ambitious queries — cross products, unanchored property paths, regular expressions over large literals — can consume unbounded time and memory. Servers are encouraged to bound execution time, memory, and result size, to apply rate limiting (responding 429), and to reject over-budget queries with 422 as required by rather than truncating them.
  • Discovery Oracle: A single query can aggregate what would otherwise require crawling an entire storage. The requirements in are what keep the service from disclosing resources or data a client is not authorized to read. Implementations are encouraged to apply the same filtering to every observable surface — results, diagnostics, and error detail alike — and to take care that response timing does not become such an oracle: evaluation time that depends on unauthorized data can reveal its existence.
  • Federation and Dereferencing: A SERVICE clause turns the storage into an HTTP client, and a dataset clause dereferenced at query time would do the same: a crafted query could probe internal networks or amplify traffic (server-side request forgery). For this reason forbids dereferencing dataset-clause IRIs and forbids SERVICE evaluation absent explicit configuration, and forbids forwarding the requesting agent's credentials when it is enabled. Deployments that enable federation are encouraged to restrict egress to an allowlist of endpoints.
  • Shared Caches: Query responses are client-specific by construction, yet cacheable by default per [[RFC10008]], whose cache key is computed over the request content rather than the requesting client. Serving them through a shared cache risks delivering one client's authorization-filtered view to another, and an over-eager cache-key normalization risks conflating two different queries. The requirements in and exist to prevent both, and deserve particular attention when a shared cache sits in front of the service.
  • Query Construction: A client that assembles query strings by concatenating untrusted input invites SPARQL injection. The consequences are bounded by this service's read-only, authorization-filtered evaluation, but real nonetheless: a broadened query can exfiltrate anything the client itself is authorized to read. Clients are encouraged to use parameterization or strict escaping. Conversely, query results can carry attacker-authored data stored in the storage — IRIs, literals, language tags — and consumers should treat them as untrusted input.
  • Request Content in Logs: Carrying the query in the request content keeps it out of typical URI-based access logs [[RFC10008]], an improvement over the GET binding of the SPARQL Protocol. Servers that log request content anyway should protect those logs accordingly, since queries can embed sensitive constants (names, identifiers, locations).

Privacy Considerations

  • Aggregation and Profiling: A single SPARQL query can join, filter, and aggregate across everything the client is authorized to read, assembling a profile that resource-by-resource retrieval would make laborious. Resource managers should understand a read grant as a grant to query: granting read access to resources also makes them joinable, aggregable, and analyzable in combination.
  • Inference: Joins can derive facts no single resource states — linking a pseudonymous profile to an identified one through a shared identifier, or inferring a sensitive attribute from co-occurring innocuous triples. The service cannot distinguish inference from retrieval; resource managers granting access to individual resources should consider what those resources disclose jointly.
  • Observation over Time: Repeated queries reveal when data appears, changes, or disappears, exposing activity patterns within the client's authorized view even when contents are not retrieved.
  • Queries as Personal Data: A query itself discloses the interests of the agent posing it. Queries retained in server logs, caches, or equivalent-resource URIs (see ) are personal data in their own right and warrant corresponding retention and access controls.
