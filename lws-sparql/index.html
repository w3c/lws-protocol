This document extends the Linked Web Storage (LWS) protocol with an optional server-managed SPARQL Query Service that evaluates SPARQL queries over the RDF content of a storage. A query travels in the content of an HTTP QUERY request, which is safe, idempotent, and cacheable. The specification defines discovery, the RDF dataset a query is evaluated against, request and response formats, error handling, and the authorization requirements that make every result client-specific.

This is an unofficial proposal, not part of the Linked Web Storage Protocol 1.0 suite. Implementing it is optional; a conforming LWS server need not support it.

Introduction

The [[!LWS10-CORE|Linked Web Storage]] protocol is a resource-centric storage system built on HTTP: clients create, read, update, and delete resources, and containers enumerate their members. Much of what a storage holds is RDF, yet the core protocol cannot ask questions that span resources. The Type Search Service of [[LWS10-INDEX]] offers a deliberately bounded conjunctive filter over resource types and indexed link relations, and leaves anything richer to alternate query formats identified by their own media types. compares the two services.

Some applications need more: joins across resources, graph patterns, property paths, value filters, and aggregation — in short, SPARQL [[!sparql11-query]]. The SPARQL Protocol [[sparql11-protocol]] carries a query either percent-encoded in the URI of a GET, subject to URI length limits and URI-based logging, or in a POST, which generic HTTP components can neither retry nor cache. The HTTP QUERY method [[!RFC10008]] resolves this: it is safe, idempotent, and cacheable, and carries the query in the request content.

This specification binds SPARQL to QUERY for LWS storages. It defines the SPARQL Query Service, discovered through the storage description like the other LWS services; the queryable dataset, derived from the storage's resources and filtered by the requesting agent's authorization; and the formats and errors of the query operation. The service is an optional extension for deployments that want graph-level query capability: one of the additional services that [[!LWS10-CORE]] lets a storage description reference, with an API defined outside the core specification.

Terminology

The terms "storage", "storage root", "storage description resource", "Storage Resource", "container", "containment", "data resource", "auxiliary resource", "resource manager", and "requesting agent" are defined by [[!LWS10-CORE]]; "Type Search Service" by [[LWS10-INDEX]]; and "RDF graph", "RDF dataset", "named graph", "default graph", and "blank node" by [[!rdf11-concepts]].

Authorization here is the storage's authorization of the request as a whole, which [[!LWS10-CORE]] lets depend on the agent, the client application making the request, and any access grants presented. What the requesting agent is "authorized to read" means what that authorization permits, and a response computed over it is client-specific.

This specification defines the following terms:

  • SPARQL Query Service — a server-managed service, of service type SparqlQueryService, that evaluates SPARQL queries [[!sparql11-query]] over a storage's queryable dataset.
  • queryable dataset — the RDF dataset a query is evaluated against: one named graph per RDF-bearing resource the requesting agent is authorized to read, named by the resource's URI, with the union of those graphs as the default graph, plus any server-managed named graphs, such as container graphs, outside the default graph (see ).
  • container graph — a server-managed named graph, named by a container's URI, holding the RDF of that container's representation (see ).
  • RDF-bearing resource — a data resource whose stored representation has a media type the server treats as an RDF concrete syntax (see ).

Discovery

A storage MAY support the SPARQL Query Service. A storage that does MUST advertise it in the service array of its storage description resource with a service object whose type equals SparqlQueryService and which MUST include a serviceEndpoint whose value is the URI of the query endpoint; other properties MAY be present. A service endpoint serves exactly one storage, the one whose description advertises it, and evaluates every query against that storage's queryable dataset. A server hosting several storages MUST advertise a distinct service endpoint for each. 

{
  "@context": [
    "https://www.w3.org/ns/cid/v1",
    "https://www.w3.org/ns/lws/v1"
  ],
  "id": "https://example.org/",
  "type": "Storage",
  "service": [
    {
      "type": "StorageRoot",
      "serviceEndpoint": "https://example.org/data/"
    },
    {
      "type": "TypeSearchService",
      "serviceEndpoint": "https://example.org/types/search"
    },
    {
      "type": "SparqlQueryService",
      "serviceEndpoint": "https://example.org/sparql"
    }
  ]
}

The service endpoint may be the same URI as another QUERY endpoint of the storage, such as the Type Search Service's [[LWS10-INDEX]]: [[RFC10008]] distinguishes query formats by Content-Type, Accept-Query can list both (for example Accept-Query: application/lws-query+json, application/sparql-query), and requests in each format are governed by that format's specification.

A storage serving both from one endpoint MUST still advertise each service in its own service object, both with the same serviceEndpoint, rather than in one object whose type lists both service types: [[LWS10-INDEX]], like this specification, requires a service object whose type equals its service type, so a client of either specification would not recognize the combined form. A server sharing an endpoint MUST keep the other uses of the endpoint's URIs distinguishable: a GET of the endpoint URI itself returns the SPARQL service description (see ), and the server MUST NOT issue a Type Search pagination URI [[LWS10-INDEX]] that it would also interpret as a SPARQL Protocol request (see ). 

[
  {
    "type": "TypeSearchService",
    "serviceEndpoint": "https://example.org/query"
  },
  {
    "type": "SparqlQueryService",
    "serviceEndpoint": "https://example.org/query"
  }
]

Service Description

A GET request to the service endpoint SHOULD return a SPARQL service description [[sparql11-service-description]], subject to ordinary content negotiation (for example text/turtle or application/ld+json). Like every response of the service, it is computed for the requesting agent: it MUST NOT enumerate named graphs, counts, or dataset statistics beyond the agent's authorized view (see ).

The description SHOULD state the supported query language versions (sd:supportedLanguage). A server whose dataset includes no server-managed graphs SHOULD assert sd:feature sd:UnionDefaultGraph, since its default graph is then the union of all its named graphs, as [[sparql11-service-description]] defines that feature. A server whose dataset includes server-managed graphs MUST NOT assert it, since those graphs are not part of the default graph (see ). It MAY list supported result formats (sd:resultFormat). If it states a default entailment regime (sd:defaultEntailmentRegime), that regime is <http://www.w3.org/ns/entailment/Simple> [[sparql11-entailment]]. It signals this specification's optional behaviors through the following features (sd:feature), defined in :

  • lws:ContainerGraphs — the queryable dataset includes container graphs, as named graphs outside the default graph. A server that includes them MUST assert this feature in any service description it provides.
  • lws:ResourceScopedQuery — the server accepts resource-scoped queries (see ) on at least some Storage Resources. A server that accepts them SHOULD assert this feature; support on a given resource is determined as describes.

The Queryable Dataset

Every request is evaluated against a queryable dataset, an RDF dataset [[!rdf11-concepts]] derived from the storage and filtered by the requesting agent's current authorization:

  • Each RDF-bearing resource in the storage that the requesting agent is authorized to read contributes one named graph. The graph name is the resource's URI exactly as the server identifies the resource for the operations of [[!LWS10-CORE]] (for example, the id of its description in a container representation); the graph is parsed from the resource's stored representation, as described below.
  • The default graph is the union of the graphs of RDF-bearing resources. A blank node in the default graph is the same blank node as in the named graph it comes from, and blank nodes from different resources are always distinct. An RDF graph is a set, so a triple occurring in several named graphs occurs once in the default graph and yields one solution there, not one per graph.
  • A server MAY include server-managed graphs, such as container graphs or graphs for auxiliary resources such as metadata resources, each named by that resource's URI. They are authorization-filtered like every other graph but are named graphs only: they MUST NOT contribute to the default graph of the queryable dataset, and a query reaches them through a GRAPH pattern or a dataset clause (a FROM clause naming one makes it part of that query's default graph; see ). The storage description resource [[!LWS10-CORE]] contributes a graph only as such a server-managed graph, whatever its media type. Each graph name identifies exactly one graph: a server-managed graph MUST NOT share its name with another graph in the dataset, and an auxiliary resource identical to its primary resource [[!LWS10-CORE]] contributes no graph beyond the primary resource's own.

Server-managed graphs describe resources as documents: a container graph types each member with the types its container lists, as in <person-4872> a schema:Person, while resource content typically describes the things those documents are about, as in <person-4872#me> a schema:Person. Keeping server-managed graphs out of the default graph keeps a query over it, such as one counting the instances of schema:Person, from counting a document alongside the person it describes.

A container graph is the RDF of a container's representation [[!LWS10-CORE]], processed as JSON-LD [[!json-ld11]] with the container's URI as the base IRI: containment (lws:items) and the description of each member, including its types. It MUST cover every page of the representation, and MUST contain exactly the members and member descriptions that a GET of the container would disclose to the requesting agent (subject, for writes, to the consistency allowance below). It is included only if the requesting agent is authorized to read the container, and a server that includes container graphs includes one for every container the requesting agent is authorized to read (see also ).

A container graph discloses exactly what reading the container discloses: for the purposes of , read authorization on a container is the authorization required to learn of the members its representation lists. Because [[LWS10-CORE]] lets totalItems be approximate, a client that needs an exact member count should count lws:items triples. Because a container representation always types the container as Container [[LWS10-CORE]], every container graph contains the triple <c> rdf:type lws:Container for its own name c, which lets a query tell container graphs from resource graphs (see ).

Whether a data resource is RDF-bearing depends only on the media type of its stored representation, not on whether the content parses. A server implementing this service MUST treat text/turtle [[!turtle]], application/ld+json [[!json-ld11]], and application/lws+json [[!LWS10-CORE]], whose documents are processed as JSON-LD, as RDF concrete syntaxes, and MAY treat others as such (for example application/n-triples [[n-triples]] or application/rdf+xml [[rdf-syntax-grammar]]). The media type is matched on its type and subtype alone, case-insensitively and ignoring parameters [[!RFC9110]], so that text/turtle; charset=utf-8 and application/ld+json; profile="https://www.w3.org/ns/lws/v1" are RDF concrete syntaxes like their bare forms. A resource that is not RDF-bearing, or whose representation fails to parse, contributes no graph and no part of one. Neither is an error: the resource's data is simply absent.

A resource's graph is parsed from its stored representation — the one whose media type is the resource's format [[!LWS10-CORE]], not any alternative the server produces through content negotiation — with the resource's URI as the base IRI [[!RFC3986]], as if the representation had been retrieved from it. Where the syntax can express a dataset, as JSON-LD [[!json-ld11]], TriG [[trig]], and N-Quads [[n-quads]] can, the resource's graph is the default graph of the parsed dataset; named graphs within the representation contribute nothing to the queryable dataset, neither as named graphs nor to the default graph.

Discarding embedded named graphs keeps every graph name identifying the resource whose content the graph holds. Otherwise a resource could assert content under the name of another resource, including one the requesting agent cannot read.

Deriving the dataset MUST NOT cause the server to retrieve resources identified by IRIs in resource content. In particular, a server MUST NOT retrieve a remote JSON-LD context [[!json-ld11]] that a representation references — directly, from another context, or through @import — unless it is explicitly configured to resolve that context, for example from a preloaded copy. A server SHOULD hold a preloaded copy of the LWS context https://www.w3.org/ns/lws/v1, which the application/lws+json documents of [[!LWS10-CORE]] reference. A representation that needs a context the server will not resolve fails to parse.

A representation using a later version of its syntax than the server implements, such as the triple terms of RDF 1.2 Turtle [[rdf12-turtle]], fails to parse for that server and contributes no graph. Resource managers relying on the service should prefer syntax the server is known to support; a server supporting a later RDF version typically also supports, and advertises, the matching SPARQL version (see ).

An IRI with a fragment identifier, such as https://example.org/data/people/person-4872#me, denotes something described by the document at the fragmentless URI, so triples about it occur in the graph named by that document's URI.

The dataset MAY be eventually consistent with respect to writes. After a write that changes a resource's contribution (creation, update, or deletion), a server SHOULD reflect the change within a bounded, implementation-defined interval; until then a query MAY miss the write, briefly observe removed data, or omit the resource's graph. Clients MUST NOT assume read-your-writes consistency and SHOULD tolerate transient staleness. This allowance covers dataset derivation only and MUST NOT be applied to authorization (see ). Data the dataset still derives from a superseded state of a resource MUST NOT contribute to a response unless the requesting agent is authorized to read the resource now and was also authorized to read it at some time while that state was current. Where a server cannot determine both, for example because the resource was deleted together with the policy that governed it, or because the server keeps no record of earlier authorization, it MUST treat the data as unreadable.

Filtering stale data by current access alone would let it outlive the authorization it was written under. A resource manager who removes content from a resource and then shares the resource, or moves it into a container with broader access, would expose the removed content to the newly authorized agent until the dataset reflects the removal, although no read of the resource could have disclosed it to that agent. Access can also broaden without any write, for example when the time constraint of an access grant begins to hold, so tracking policy changes does not suffice. The simplest conforming approach is to withhold a resource's graph from every response from the moment a write to the resource is accepted until the dataset reflects it: such a server never serves a superseded state and needs no record of earlier authorization.

A server will typically maintain a materialized index, such as a quad store mirroring the storage, rather than parse resources at query time. That is an implementation detail: the observable dataset is the one defined here, and applies to every response however the dataset is materialized.

Queries are evaluated under simple entailment [[!sparql11-query]]: the dataset contains exactly the triples derived as described in this section, and a server MUST NOT add inferred triples to it.

Apart from permitted SERVICE evaluation (see ), a query's result MUST depend on nothing but the query (its relative IRIs resolved as describes), the dataset it is evaluated against, and the values the query language makes depend on the evaluation itself, such as those of NOW(), RAND(), and UUID() [[!sparql11-query]]. A server MUST NOT evaluate an extension function or other non-standard feature, such as a property function or a search predicate, whose result depends on any other data, such as a full-text or geospatial index built over the whole store rather than over that dataset, the server's files or databases, or another storage. A server MAY offer such features when they are computed over that dataset alone.

Dataset Clauses (FROM, FROM NAMED)

A query MAY carry dataset clauses (FROM, FROM NAMED) [[!sparql11-query]]. They select from the queryable dataset and never extend it. A dataset-clause IRI selects the graph whose name it equals under the simple string comparison by which RDF compares IRIs [[!rdf11-concepts]]; a server MUST NOT normalize either IRI before comparing — not in case, percent-encoding, default ports, or dot-segments, nor by converting between URI and IRI forms. Any other IRI — one identifying a resource the requesting agent is not authorized to read, a resource that is not RDF-bearing, a resource that does not exist, or a URI outside the storage — MUST be treated as naming an empty graph, and these cases MUST be indistinguishable in the response's status code, header fields, and content (see ), so that dataset clauses cannot reveal which unreadable resources exist. A server MUST NOT dereference an IRI to construct a graph for a dataset clause.

As [[sparql11-query]] specifies, dataset clauses replace the default graph and named graphs rather than add to them: with FROM NAMED but no FROM the default graph is empty, not the union, and with FROM but no FROM NAMED there are no named graphs, so a GRAPH pattern matches nothing.

Federated Query (SERVICE)

A SERVICE clause [[sparql11-federated-query]] has the query processor contact a remote endpoint. A server MUST NOT evaluate SERVICE clauses unless explicitly configured to; otherwise a query containing one, SILENT or not, MUST be rejected with 422 (see ). A server that evaluates them MUST NOT forward the requesting agent's credentials to the remote endpoint and SHOULD restrict the endpoints it contacts (see ).

Apart from permitted SERVICE evaluation, a server MUST NOT, in order to evaluate a query, retrieve any resource identified by an IRI in the query or the data — whether to dereference a dataset-clause IRI (see ), to evaluate an extension function or other non-standard feature that retrieves remote content, or otherwise.

SPARQL Query Operation

QUERY [SparqlQueryService]

A client queries by sending an HTTP QUERY request [[!RFC10008]] to the advertised serviceEndpoint URI, as-is, with the SPARQL query as the request content. The Content-Type header field identifies the query format and MUST be present (see ). Every server MUST support the application/sparql-query format [[!sparql11-query]]: a single query string in the SPARQL query language, encoded in UTF-8, as in the SPARQL Protocol's query via POST directly [[sparql11-protocol]]. A server MAY accept other query formats, each identified by its own media type; applies whatever the format. QUERY is safe and idempotent [[!RFC10008]], as [[!RFC9110]] defines those terms: a query never alters server state and MAY be repeated, retried, or cached. Because the query travels in the content rather than the request URI, it is not subject to the request-URI length limits of the SPARQL Protocol's query-string binding.

This binding defines no URI query parameters; in particular, the SPARQL Protocol parameters query, default-graph-uri, and named-graph-uri are not used. A QUERY request whose target URI carries any of them is rejected, not evaluated with the parameter ignored (see ): a client sending default-graph-uri or named-graph-uri expects them to select the dataset, as they do in the SPARQL Protocol's query via POST directly [[sparql11-protocol]], and would otherwise receive the result of a different query. The dataset is the queryable dataset (see ), possibly restricted by the query's own dataset clauses (see ); a server that also accepts the SPARQL Protocol bindings handles their parameters as describes. In a query without a BASE declaration, relative IRIs are resolved [[!RFC3986]] against the request's target URI [[!RFC9110]]: the service endpoint, or the target resource of a resource-scoped query (see ). A query with BASE resolves them as [[!sparql11-query]] specifies.

The baseline query language is SPARQL 1.1 Query [[!sparql11-query]]. A server MAY implement a later version, such as SPARQL 1.2 [[sparql12-query]], and SHOULD advertise its supported versions in its service description (see ); a portable client MUST NOT rely on features beyond SPARQL 1.1 without confirming their support there. Of the four query forms the language defines [[!sparql11-query]], a server MUST support SELECT, ASK, and CONSTRUCT. It SHOULD support DESCRIBE, but because [[!sparql11-query]] leaves the content of a DESCRIBE result implementation-defined, it MAY decline it.

SPARQL update operations [[sparql11-update]] are outside the scope of this specification: the update language is a distinct language with its own media type, QUERY is safe, and a server MUST NOT execute any state-changing operation in response to it [[!RFC10008]]. gives the status codes for unsupported forms and for update requests.

A server SHOULD advertise its accepted query formats in the Accept-Query response header field [[!RFC10008]], for example in response to an OPTIONS request on the service endpoint, whose Allow header also shows that QUERY is supported. The value MUST include application/sparql-query. Accept-Query lists only query-format media types, not language features, query forms, or dataset contents. A client that receives 415 MAY consult it to select a supported format.

A browser-based client's cross-origin request is preceded by a CORS preflight (OPTIONS) [[RFC10008]] [[FETCH]] when it uses QUERY, which is not a CORS-safelisted method, a Content-Type of application/sparql-query, or an Authorization header field. A server intended for such clients answers preflights for the service endpoint, listing QUERY in Access-Control-Allow-Methods and Content-Type and Authorization in Access-Control-Allow-Headers. Because browsers expose only CORS-safelisted response header fields to scripts, it also lists in Access-Control-Expose-Headers any others clients need to read, such as Accept-Query, ETag, Link, or WWW-Authenticate. A preflight carries no credentials, so its response cannot depend on the requesting agent; it is also distinct from an OPTIONS request a client sends itself to discover Accept-Query.

Authentication

The service endpoint is a protected resource of the storage it serves. Requests to it, QUERY requests and service-description GET requests alike, are authenticated as [[!LWS10-CORE]] requires for that storage's resources: a server validates an access token as it would one presented to a Storage Resource of that storage, treating that storage as the one containing the target, so the token's audience is that storage. A 401 (Unauthorized) response carries the WWW-Authenticate challenge and the Link header identifying the storage that [[!LWS10-CORE]] requires. Before requesting a token, a client checks that the discovered protected resource metadata and the storage's StorageRoot service endpoint have the requested URI's scheme and authority [[!LWS10-CORE]]; a server therefore MUST advertise a service endpoint with the same scheme and authority as the storage's StorageRoot service endpoint.

A request whose credentials fail validation, such as an expired access token, MUST be rejected with 401. A server MUST NOT evaluate it as though it carried no credentials, and MUST NOT answer it with an empty result: a client could not otherwise tell a failed authentication from absent data.

A request without credentials comes from an unauthenticated agent. A server MAY evaluate it over what such an agent is authorized to read, if anything, or MAY reject it with 401 so that the client can obtain an access token. A server MAY also restrict the service itself, for example to particular agents or clients, rejecting other requests with 403 (Forbidden). These decisions MUST NOT depend on the query, and depend on the storage's content only through the server's policy for the service, wherever that policy is kept: only the request's credentials and that policy determine them.

Responses

A successful query returns 200 (OK) whatever the result's size: an empty solution sequence, an empty graph, and an ASK result of false are all successes. The response media type depends on the query form and the request's Accept header field:

  • For SELECT and ASK, every server MUST be able to produce application/sparql-results+json [[!sparql11-results-json]], and MAY offer other formats, such as application/sparql-results+xml [[rdf-sparql-XMLres]] and, for SELECT only (they define no ASK form), text/csv or text/tab-separated-values [[sparql11-results-csv-tsv]].
  • For CONSTRUCT and DESCRIBE, every server MUST be able to produce text/turtle [[!turtle]], and MAY offer other RDF serializations, such as application/ld+json [[json-ld11]] or application/n-triples [[n-triples]].

A request without an Accept header field receives the mandatory format for its query form. Otherwise the server selects among the formats it offers for that form by proactive negotiation [[!RFC9110]], honoring the request's preferences, and MAY therefore return a non-mandatory format the request prefers [[!RFC10008]]. Because the mandatory format is always available, a request whose Accept admits it always receives an acceptable format. Many clients request JSON generically, so for SELECT and ASK a server SHOULD treat an Accept header field that admits application/json but none of the result formats it offers as accepting SPARQL JSON results, and return them with Content-Type: application/json rather than respond 406.

No pagination is defined for query results: the LWS pagination model of [[!LWS10-CORE]] does not apply to the SPARQL Query Service. Range requests have the semantics they have for GET [[!RFC10008]], so a server MAY ignore a Range header field [[!RFC9110]]; this specification adds no range unit for query results. Clients page through results with the solution modifiers ORDER BY, LIMIT, and OFFSET [[!sparql11-query]], the query-language features [[!RFC10008]] expects to be used instead of HTTP range requests.

OFFSET paging is only as stable as the dataset: a concurrent write can shift solutions between pages. Clients that need a stable enumeration should impose a total order with ORDER BY. A deep OFFSET is also costly, since a server generally evaluates every solution it skips; a client can instead resume after the last solution received by filtering on the ordering keys, which together need to identify a solution uniquely. A query ordered by ORDER BY STR(?name) STR(?person), for example, resumes after Bob Hart by adding FILTER(STR(?name) > "Bob Hart" || (STR(?name) = "Bob Hart" && STR(?person) > "https://example.org/data/people/person-4873#me")). Comparing STR() values keeps the filter consistent with the order and applicable to language-tagged literals, which > does not compare with simple literals [[!sparql11-query]].

A server MAY bound the work, execution time, memory, or result size a query is allowed to consume (see for how these bounds are chosen and counted). A server that cannot complete a query within its bounds MUST fail the request (see ); it MUST NOT return a truncated result presented as complete, nor otherwise narrow the query to fit its bounds. A server streaming a result can reach such a bound, or fail otherwise, after sending the status code and part of the content, when the status code can no longer be changed. It MUST then end the message so the client can detect that it is incomplete — for example, in HTTP/1.1, by closing the connection without the final chunk of a chunked transfer coding [[RFC9112]], or, in HTTP/2 and HTTP/3, by resetting the stream — and MUST NOT complete it as though the result were whole. A client MUST NOT treat an incomplete response message as a complete result.

A server MAY implement conditional QUERY requests: because the selected representation of a QUERY is that of a GET of the equivalent resource [[!RFC10008]], it MAY emit a validator (such as an ETag) and honor conditional header fields such as If-None-Match on a repeated query. Any such validator MUST be scoped to the requesting agent's authorized view (see ). A strong validator [[RFC9110]] suits only content that is identical on every evaluation it validates. Blank-node labels, and the order of solutions that ORDER BY does not fix, can differ between evaluations over an unchanged dataset, so a server that does not hold them stable emits a weak validator. On a resource-scoped query (see ), the validator, and every conditional header field of the request, applies to the query's result, not to the target resource: a client cannot make a query conditional on the target's state by sending the target's own ETag.

Errors

Servers report outcomes with standard HTTP status codes [[!RFC9110]], in particular:

Condition Response
The content is not a syntactically valid SPARQL query [[!sparql11-query]], including a SPARQL update sent as application/sparql-query (the update language is a separate grammar). MUST be 400 (Bad Request).
The Content-Type header field is missing or inconsistent with the content, either of which [[!RFC10008]] requires a server to reject. MUST be 400 (Bad Request).
The target URI of a QUERY request carries a SPARQL Protocol parameter (query, default-graph-uri, or named-graph-uri; see ). MUST be 400 (Bad Request).
The request's credentials fail validation (see ). MUST be 401 (Unauthorized).
The request carries no credentials (see ). MAY be 401 (Unauthorized), rather than evaluating the request for an unauthenticated agent.
The server does not permit the request to use the service (see ). MAY be 403 (Forbidden).
The Content-Type identifies a query format the server does not support. A request carrying application/sparql-update is always such a request; application/sparql-query never is (see ). MUST be 415 (Unsupported Media Type), and SHOULD include an Accept-Query header field [[!RFC10008]] listing the formats the server accepts.
The Accept header field excludes every media type the server can produce for the query's form. A request that omits Accept or admits the mandatory format (see ) never qualifies. MUST be 406 (Not Acceptable) [[!RFC10008]].
A syntactically valid query the server declines because of its contents, including a query form it does not support (see ), a SERVICE clause it will not evaluate (see ), complexity beyond what it chooses to support, or a query exceeding a result-size bound or a bound on work counted over the authorization-filtered dataset (see ). MUST be 422 (Unprocessable Content), which [[!RFC9110]] defines and [[!RFC10008]] suggests for a query understood but unprocessable due to its contents. It tells the client that repeating the same query will not succeed unless the data the requesting agent is authorized to read changes.
The server cannot complete a query it would otherwise process because the query exceeds a bound on elapsed time or memory, or because the server is overloaded (see ). SHOULD be 503 (Service Unavailable) [[!RFC9110]], optionally with a Retry-After header field indicating when to repeat the query. MUST NOT be 422, since the same query can succeed when the server is less loaded.
The request exceeds a rate limit. SHOULD be 429 (Too Many Requests) [[RFC6585]], likewise optionally with Retry-After.
The request content exceeds a size bound, which a server MAY set. SHOULD be 413 (Content Too Large) [[!RFC9110]].

A query that exceeds a bound fails with one of the status codes above, never with a truncated or narrowed result (see ). Referencing data the requesting agent is not authorized to read is never an error: the data is simply absent from the queryable dataset, and keeps responses from revealing it. This concerns only data within the dataset; it never turns a failed authentication, or a refusal to serve the requesting agent, into an empty result (see ).

A query that exceeds a bound on elapsed time or memory on every attempt receives 503 each time. A client that keeps receiving it for one query can make the query cheaper, for example with more selective patterns or a smaller LIMIT, rather than repeat it unchanged.

An error response may describe the problem, for example with a parser diagnostic, in a format this specification does not define. applies to diagnostics as to results.

Caching

A QUERY response is cacheable [[!RFC10008]]. The query, as request content, is part of the cache key itself ([[!RFC10008]], Section 2.7) and cannot be conveyed in the Vary header field [[RFC9110]], which names only request header fields. A server that negotiates the response format on Accept (see ) MUST list Accept in Vary, so that caches do not reuse a representation across response formats.

Every result is evaluated against an authorization-filtered dataset and is therefore client-specific (see ), yet its cache key is computed from the request content rather than its authorization. A server MUST ensure that no shared cache serves an authorization-filtered response in answer to a request authorized differently: except as follows, it MUST mark such responses so that they are not reused across requesting agents (for example with Cache-Control: private or no-store [[!RFC9111]]) and MUST vary any cached entry on the credential that scopes the result. The exception is a response to a request without credentials, which reflects only what an unauthenticated agent may read and is the same for every such request: a server MAY let shared caches store and reuse it (for example with Cache-Control: public), provided its authorization of unauthenticated requests depends on nothing else about a request, such as its source address, and the response lists in Vary every request header field that can carry credentials (such as Authorization), so that no cache reuses it for a request that carries them.

A shared cache does not store a response to a request carrying an Authorization header field unless the response explicitly permits it ([[RFC9111]], Section 3.5), and the requirements above ensure none does. A private cache, such as a browser's, can still reuse a response after the requesting agent's access has been narrowed, or for another user of the same browser. For a response to a request that carries credentials, a server SHOULD therefore send Cache-Control: private, no-cache, so that each reuse is revalidated against current authorization, and SHOULD list in Vary the request header fields that carry credentials, such as Authorization. A validator (see ) makes revalidation cheap.

A query using NOW(), RAND(), UUID(), or STRUUID() [[!sparql11-query]] can return a different result on every evaluation of an unchanged dataset. A server SHOULD mark responses to such queries Cache-Control: no-store and SHOULD NOT emit a validator for them.

[[!RFC10008]] permits a cache to normalize request content when computing the cache key, for a SPARQL query for example by collapsing insignificant whitespace or comments. Normalization affects only the cache key, never the request, but an incorrect one can serve one query's results for another; a cache without specific knowledge of application/sparql-query is safest comparing content byte for byte.

Equivalent Resources and Result Resources

[[!RFC10008]] lets a response name a resource representing the query's results (Content-Location) or an equivalent resource from which the same query's results can later be retrieved with GET (Location). Because results are authorization-filtered and client-specific (see ), this specification defines neither. A server that exposes one MUST subject every access to it to the same authorization filtering, MUST prevent its reuse for requests authorized differently, and SHOULD keep sensitive portions of the query out of its URI [[!RFC10008]].

SPARQL Protocol Bindings

Many SPARQL clients support only the SPARQL Protocol's bindings of the query operation [[sparql11-protocol]] — query via GET, via URL-encoded POST, and via POST directly — and some intermediaries do not forward QUERY. A server MAY therefore also accept these bindings at the service endpoint. A server that does MUST evaluate such a request exactly as a QUERY request carrying the same query, against the same queryable dataset and subject to every requirement of this specification, except that:

  • the parameters default-graph-uri and named-graph-uri, if present, select from the queryable dataset exactly as the corresponding dataset clauses (FROM and FROM NAMED) do (see ), never extending it, and take precedence over the query's own dataset clauses, as [[sparql11-protocol]] requires;
  • a GET request to the service endpoint without a query parameter remains a request for the service description (see ).

The GET binding exposes the query to URI length limits and URI-based logging (see ), and generic HTTP components treat POST as neither safe nor idempotent, so they neither retry nor cache it. A client that can use QUERY SHOULD prefer it.

The SPARQL 1.2 Protocol [[sparql12-protocol]] acknowledges QUERY as an optional binding used like query via POST directly, with no SPARQL-specific requirements of its own. The binding of is consistent with it but narrower: it defines no URI query parameters, so only dataset clauses in the query select a dataset, and a request carrying default-graph-uri or named-graph-uri fails rather than having them ignored. It also fixes the status codes of where the SPARQL Protocol leaves servers a choice.

Resource-Scoped Queries

The service endpoint evaluates queries against the whole storage. A server MAY also accept QUERY requests carrying application/sparql-query directly on Storage Resources, scoping the dataset to the target. The resources in scope are:

  • the target;
  • if the target is a container, every resource it transitively contains, including the containers among them;
  • the auxiliary resources [[!LWS10-CORE]] of each of these.

On the storage root, the restricted dataset is the whole queryable dataset, as at the service endpoint. On any other target, it consists of the graphs of the queryable dataset named by resources in scope: the graph of each RDF-bearing resource and, where the server includes them, the container graph of each container and the server-managed graphs of auxiliary resources. A query on a container therefore reaches the container graphs of its sub-containers as well as its own.

The restricted dataset is derived and authorization-filtered exactly as in , its default graph being the union of the in-scope graphs of RDF-bearing resources, and all other requirements apply unchanged. A data resource that is not RDF-bearing, or whose representation fails to parse, contributes no graph (see ), so a query on it is evaluated against an empty dataset and succeeds with an empty result. Access to the target itself is governed by [[!LWS10-CORE]]: a request whose target the requesting agent is not permitted to read fails as any read of it would, before any query evaluation. Dataset clauses select only from the restricted dataset; an IRI naming a graph outside the scope names an empty graph, indistinguishably from the cases of . Because relative IRIs resolve against the target (see ), <> denotes the target itself, so GRAPH <> { … } matches within its own graph.

Support for resource-scoped queries is OPTIONAL and per resource. A server advertises it as [[!RFC10008]] provides, by including QUERY in the Allow header field of responses to the resource (for example to OPTIONS) and by the Accept-Query response header field. A QUERY request on a resource without such support fails as any unsupported method does: 405 (Method Not Allowed) with an Allow header field [[!RFC9110]].

Resource-scoped queries give SPARQL the target scoping the QUERY method natively has, "a query over the data reachable from this resource", without minting per-scope endpoints, and compose naturally with the LWS containment hierarchy.

Security and Authorization

Servers MUST enforce authorization. Every response, at the service endpoint or on a resource-scoped target, is computed from a queryable dataset that contains only the content of resources the requesting agent is authorized to read (see ).

Unauthorized data MUST be omitted entirely. A server MUST NOT allow a requesting agent to learn, from the status code, header fields, or content of the service's responses — solutions, constructed triples, graph names bound by a GRAPH variable, ASK results, error responses, or diagnostics — that a specific resource, graph, or triple exists, or that a specific term occurs in the storage at all, without the required authorization. The result is a dynamically evaluated, client-specific view of the storage. Response timing cannot in general be made fully independent of the data a server holds, and these requirements do not extend to it; a server SHOULD nevertheless limit how far response timing depends on data the requesting agent is not authorized to read (see ).

The same applies to every value a response exposes and to every decision about whether and how a query is answered:

  • Every value a response exposes, including every aggregate (such as COUNT, SUM, or GROUP_CONCAT), MUST be computed over the authorization-filtered dataset, never over the storage as a whole; a value reflecting unauthorized data would reveal that data's existence.
  • Every decision about whether and how a query is answered — including whether a server rejects it as too complex, whether it exceeds a result-size bound, and which status code results — MUST NOT depend on data the requesting agent is not authorized to read, except as the next item allows; otherwise a query whose cost depends on such data could reveal it through the status code alone. A server that estimates cost from dataset statistics MUST compute them over the authorization-filtered dataset or use estimates independent of the data. A bound on the work a query may do meets this requirement only if the work is counted over the authorization-filtered dataset, for example as the number of intermediate solutions produced from authorized graphs.
  • A decision that rests on a measurement of the evaluation itself or of the server's state, such as elapsed time, memory use, or load, is exempt, because such a measurement depends on how the server stores and indexes data and on the other requests it is serving. Two further requirements keep a bound on such a measurement from revealing unauthorized data through whether it ends a query. First, a server MUST apply authorization filtering when it selects the graphs a query is evaluated over, so that no solution, intermediate or final, is computed from a graph the requesting agent is not authorized to read; it MUST NOT evaluate a query over unfiltered data and filter the results afterward. A query's work then depends on authorized data only, and a measurement depends on unauthorized data only through the server's storage and indexes, for example through index entries a lookup passes over. Second, a server that bounds the cost of queries SHOULD do so primarily with a bound on work counted over the authorization-filtered dataset (see the previous item), and SHOULD set its bounds on elapsed time and memory high enough that a query within its work bound reaches them rarely other than under load. That remaining dependence is part of the response timing that the requirements above do not extend to, even when a bound ends a query with an error status. gives the status code for a query ended by such a bound.

Authorization filtering MUST be evaluated against the requesting agent's current access when the request is served, not against a cached or precomputed view: once an authorization (such as an access grant) is revoked or narrowed, the affected graphs and triples MUST NOT contribute to any later response. The eventual-consistency allowance of MUST NOT be extended to authorization; nor does broadening an authorization expose content that a resource held only before the requesting agent was authorized to read it (see ). A server MAY maintain a materialized dataset or index for performance, but MUST apply current authorization as a filter over it on every request.

Client-specific responses are nonetheless cacheable by default [[!RFC10008]]; specifies how a server keeps a cache from reusing one for a request authorized differently.

Every additional query format a server accepts at the service endpoint, and every other query surface it exposes over the storage, MUST uphold these requirements, so that no query mechanism becomes a discovery oracle for resources or data the requesting agent is not authorized to read. [[LWS10-INDEX]] places the same requirement on extension query mechanisms; a SPARQL Query Service deployed alongside a Type Search Service meets it by conforming to this section.

Security Considerations

  • Resource Exhaustion: SPARQL is far more expressive than the Type Search filter of [[LWS10-INDEX]], and adversarial or merely ambitious queries — cross products, unanchored property paths, regular expressions over large literals — can consume unbounded time and memory. Servers are encouraged to bound the work, execution time, memory, and result size of queries, to rate-limit (responding 429), and to fail over-budget queries with the status codes requires rather than truncate them.
  • Discovery Oracle: One query can aggregate what would otherwise require crawling an entire storage; keeps the service from disclosing what the requesting agent is not authorized to read. Implementations are encouraged to filter every observable surface alike: results, diagnostics, and error detail. Extension functions are such a surface: triple stores commonly provide full-text or geospatial search through indexes built over the whole store, which answer from unauthorized data unless restricted to the dataset a query is evaluated against (see ). Limits are such a surface too: a query whose cost depends on unauthorized data could reveal it through whether the query succeeds, which therefore forbids for limits defined over the query and the authorized data. Timing deserves the same care: evaluation time that depends on unauthorized data can reveal its existence even where content does not, whether through how long a response takes or through whether a bound on elapsed time or memory ends the query with 503. A 503 is the more dangerous of the two, since one response answers what timing reveals only statistically. therefore requires selecting the graphs a query is evaluated over by authorization before evaluating it, so that a query's work depends on authorized data only, and recommends limiting cost chiefly with work bounds counted over authorized data. What remains is the dependence of evaluation time on the storage's own indexes, a far weaker signal.
  • Federation and Dereferencing: A SERVICE clause turns the storage into an HTTP client, and so would a dataset clause dereferenced at query time, an extension function that fetches remote content, or a remote JSON-LD context retrieved while deriving the dataset from client-authored content. A crafted query or resource could then probe internal networks or amplify traffic (server-side request forgery), and fetched content would make the dataset depend on whatever the remote server returns. , , and therefore forbid all such retrieval except explicitly configured context resolution and explicitly configured SERVICE evaluation, and forbid forwarding the requesting agent's credentials even then. Deployments that enable federation are encouraged to restrict egress to an allowlist of endpoints.
  • Shared Caches: Responses are client-specific yet cacheable by default [[RFC10008]], under a cache key computed from the request content, not its authorization. A shared cache could deliver one requesting agent's view to another, and an over-eager cache-key normalization could conflate two queries; addresses both and deserves particular attention when a shared cache fronts the service.
  • Query Construction: A client that builds query strings by concatenating untrusted input invites SPARQL injection. Read-only, authorization-filtered evaluation bounds the consequences, but a broadened query can still exfiltrate anything the client itself is authorized to read; clients are encouraged to use parameterization or strict escaping. Conversely, results can carry attacker-authored data from the storage (IRIs, literals, language tags), which consumers should treat as untrusted input.
  • Request Content in Logs: Carrying the query in the request content keeps it out of typical URI-based access logs [[RFC10008]], unlike the SPARQL Protocol's GET binding, which exposes the queries of requests that use it on a server that accepts it (see ). Servers that log request content should protect those logs, since queries can embed sensitive constants (names, identifiers, locations).

Privacy Considerations

  • Aggregation and Profiling: A single query can join, filter, and aggregate across everything the requesting agent is authorized to read, assembling a profile that resource-by-resource retrieval would make laborious. Resource managers should understand a read grant as a grant to query: readable resources are also joinable, aggregable, and analyzable in combination.
  • Inference: Joins can derive facts no single resource states, such as linking a pseudonymous profile to an identified one through a shared identifier, or inferring a sensitive attribute from co-occurring innocuous triples. The service cannot distinguish inference from retrieval; resource managers granting access to individual resources should consider what those resources disclose jointly.
  • Observation over Time: Repeated queries reveal when data appears, changes, or disappears, exposing activity patterns within the requesting agent's authorized view even when contents are not retrieved.
  • Lagging Removal: Because the dataset may lag writes (see ), content removed or deleted, for example to withdraw a disclosure, can remain queryable until the server reflects the change, though only by agents that could read the resource before the removal and still can. Servers are encouraged to keep that interval short and to reflect removals at least as promptly as additions. Resource managers should not rely on a removal taking effect at once; where it matters, narrowing access first does, since authorization changes apply to the very next query. Sharing a resource right after removing content from it is safe: the removed content stays hidden from the newly authorized agent.
  • Queries as Personal Data: A query discloses the interests of the agent posing it. Queries retained in server logs, caches, or equivalent-resource URIs (see ) are personal data in their own right and warrant corresponding retention and access controls.

Relationship to the Type Search Service

The two services are complements. The Type Search filter is the bounded-cost baseline: its grammar is frozen, its cost predictable, and a portable client can rely on it. SPARQL is the opt-in power tool, correspondingly costlier to evaluate and to guard. application/sparql-query is the kind of alternate query format [[LWS10-INDEX]] anticipates, here given a service of its own; one endpoint may serve both (see ).

The services also see different data. A Type Search filter matches the types a resource itself bears, which a server derives, per [[LWS10-INDEX]], from Link headers, from server-intrinsic classes such as lws:DataResource and lws:Container, and optionally from content. The queryable dataset holds resource content (see ), where types are usually asserted of the things a resource describes, typically fragment IRIs such as <person-4872#me>, rather than of the resource. GRAPH ?r { ?s a schema:Person } therefore selects every resource whose content mentions a person and, where the server includes container graphs, every container that lists a member of that type; neither is the set of resources a Type Search filter on schema:Person selects.

A Type Search type filter can be approximated in SPARQL only over types present in the dataset as types of the resources themselves. Container graphs provide them: each member appears in its container's graph with the types its container representation lists [[LWS10-CORE]], so a type filter over those types translates to a graph pattern over the container graphs, of the form GRAPH ?container { ?container lws:items ?resource . ?resource a ?type } (see the container-graph example in ). The translation differs from Type Search in three ways:

  • Types derived for Type Search but not listed in container representations, such as types a server derives from resource content [[LWS10-INDEX]], have no SPARQL counterpart.
  • The storage root is a member of no container, so the translation never matches it.
  • Authorization differs. Type Search lists a resource only if the requesting agent is authorized to read that resource, while a container graph lists whatever reading the container discloses (see ). [[LWS10-CORE]] leaves it to the server which members a container representation discloses, so it can list members the requesting agent cannot read, and the translation then returns them too.
