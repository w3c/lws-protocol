The recommendations described in Best Current Practice for OAuth 2.0 Security [[RFC9700]] apply to this specification.

Transport Security

Transport Layer Security (TLS) is an important mechanism to prevent against tampering, spoofing, and information disclosure. TLS-protected communication can be verified according to [[RFC6125]]. Implementation security considerations can be found in "Recommendations for Secure Use of Transport Layer Security (TLS) and Datagram Transport Layer Security (DTLS)" [[RFC9325]].

Token Security

Bearer tokens and digital credentials are vulnerable to theft and replay. Mitigations include using a reasonably short lifetime, binding tokens to a particular audience, and storing tokens securely.

  • Short Lifetimes: Authorization servers that assign lifetimes of 300 seconds (5 minutes) or less to access tokens can limit the potential exposure of an exfiltrated credential.
  • Audience Binding: Binding an access token to a specific destination server, by means such as the aud claim, protects against the token being replayed to a different server. An access token whose audience includes more than one server can be replayed by any of those servers to the others, which authorization servers avoid by issuing tokens with a single storage URI as the audience. Applications that handle credentials with an unrestricted audience need to be careful when sending these credentials to other entities, especially untrusted authorization servers. If a credential issuer is unable to restrict the audience of a token, clients can use a mechanism such as OAuth 2.0 Token Exchange [[RFC8693]] to create audience-constrained credentials before interacting with an authorization server in a different security domain.
  • Sender-Constrained Tokens: A bearer token can be used by any party that obtains it, and an audience restriction does not prevent an exfiltrated token from being replayed to the intended storage server. Because the audience is a storage, a stolen token is usable for every resource within that storage that the agent is authorized to access. Binding an access token to a client key, such as with OAuth 2.0 Demonstrating Proof of Possession (DPoP) [[RFC9449]], limits use of a stolen token to the holder of that key. A protected resource metadata document can advertise the DPoP proof algorithms that a storage server supports and whether it requires DPoP-bound access tokens, using the dpop_signing_alg_values_supported and dpop_bound_access_tokens_required parameters defined in [[RFC9728]].
  • Secure Storage: Applications that persist credentials need to ensure that these objects are stored safely. Any time an unencrypted token is stored in a browser's localStorage, in URLs, or in logs, that token is more susceptible to an exfiltration attack.

Resource Discovery

A client learns the location of an authorization server from a response sent by a storage server that the client might not trust. The following considerations apply to this discovery process.

  • Untrusted Metadata: A malicious storage server can direct a client to an authorization server that the client does not trust, and a client that presents an authentication credential to that authorization server discloses the credential. Clients can reduce this risk by applying their own policy about which authorization servers to trust. The checks in , which require that the protected resource metadata describe the requested resource on the same server, prevent a server from presenting metadata that belongs to a different resource server. The impact of disclosure is also reduced when a client uses an authentication credential whose audience is limited to the authorization server to which it is sent.
  • Storage Binding: A client obtains the storage URI from a Link header in a response from the storage server. A malicious server can supply the URI of a different storage, causing the client to obtain an access token for that storage and present it to the malicious server, which can then replay it. For this reason, a client is required to confirm, using the storage description, that the requested URI is served from the same origin as the storage root before requesting an access token, as described in .
  • Server-Side Request Forgery: The resource_metadata URL in a challenge, the storage URI in a Link header, and the issuer identifiers in a protected resource metadata document are chosen by the storage server, and a client retrieves the documents they identify. Clients that perform this retrieval on behalf of other parties, such as a server-side application, are exposed to server-side request forgery, as described in Section 7.7 of [[RFC9728]]. Precautions include restricting retrieval to the https scheme and blocking requests to internal IP address ranges.

Access Requests and Grants

  • Servers are strongly encouraged to apply authorization rules to both the access request and access grant endpoints. Write access to the access grant endpoint, in particular, should be restricted to authorized storage controllers and specific clients.
  • When an agent creates an access request, the server is encouraged to verify that the assignee value in the request is associated with the authenticated identity of the requesting agent.
  • Because the access request endpoint accepts content from external agents, servers are encouraged to implement measures to prevent abuse, such as rate limiting, payload size restrictions, or requiring authentication before accepting submissions. Without such protections, the endpoint may be vulnerable to spam, resource exhaustion, or other forms of unwanted content.

Notifications

  • Information Disclosure: Notifications may reveal the existence or modification patterns of resources. Access control on subscriptions and on individual notification delivery MUST be consistent with access control on the underlying resources.
  • Subscription Abuse: Rate limiting and endpoint verification are suggested to prevent abuse of the subscription mechanism.
