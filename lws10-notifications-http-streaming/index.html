This document defines an HTTP streaming notification suite for the Linked Web Storage protocol. A subscriber obtains an outbox URL from a subscription and reads notification envelopes from a long-lived HTTP response as JSON Sequence and other optional representations.

This is an unofficial proposal.

Introduction

The [[LWS10-CORE|Linked Web Storage]] protocol defines a notification data model and a subscription mechanism. This document describes the HTTP streaming notification suite. A subscriber creates an HTTP streaming subscription and receives an outbox URL. The subscriber sends an HTTP GET request to the outbox and keeps the response open while the server writes notification envelopes.

The response uses HTTP content negotiation to select JSON Sequence or an optional representation.

An experimental prototype is available in elf-pavlik/lws-http-stream.

Terminology

The terms "notification", "subscription", "subscriber", "notification suite", "storage description resource", and "agent" are defined by the Linked Web Storage Protocol [[!LWS10-CORE]].

This specification defines the following additional terms:

  • Outbox is a URL returned in a subscription response. A subscriber reads notifications from the outbox with an HTTP GET request.

Creating an HTTP Streaming Subscription

When a client creates an HTTP streaming notification subscription, the value of the type field MUST be HttpStreamingSubscription. This subscription type does not define additional request fields. 

POST /subscriptions HTTP/2
Host: notification.example
Authorization: Bearer <access-token>
Content-Type: application/lws+json

{
  "@context": ["https://www.w3.org/ns/lws/v1"],
  "type": "HttpStreamingSubscription",
  "topic": ["https://storage.example/st793u"]
}

A successful response body has these additional requirements:

  • type: the value of this property MUST be a string equal to HttpStreamingSubscription.
  • outbox: REQUIRED. The URL from which the subscriber reads the notification stream. The subscriber selects a representation with the Accept request header. 
HTTP/2 200 OK
Content-Type: application/lws+json
Accept: application/x-ndjson, application/jsonl, application/cbor-seq, application/x-jelly-rdf
Location: https://notification.example/ise0sx

{
  "@context": ["https://www.w3.org/ns/lws/v1"],
  "type": "HttpStreamingSubscription",
  "subscription": "https://notification.example/ise0sx",
  "outbox": "https://notification.example/mnmmkr"
}

Establishing an HTTP Streaming Connection

After obtaining an outbox URL, the subscriber sends an HTTP GET request to that URL with an Accept header that lists one or more supported media types.

Notifications section of [[LWS10-CORE]] defines the notification envelope and subscription model. 

GET /mnmmkr HTTP/2
Host: notification.example
Accept: application/json-seq

A successful response MUST use status 200 and the media type selected by content negotiation. The server keeps the response body open and writes notification envelopes defined by [[!LWS10-CORE]] as changes occur. The envelopes form an ordered sequence. HTTP chunk boundaries do not define notification boundaries. The stream ends when the server closes the response or the subscriber aborts the request.

The response MUST include Cache-Control: no-store and Vary: Accept. 

HTTP/2 200 OK
Content-Type: application/json-seq
Cache-Control: no-store
Vary: Accept
Accept: application/json-seq, application/x-ndjson, application/jsonl, application/cbor-seq, application/x-jelly-rdf

Clarify heartbeat messages that keep connections alive.

Representations

An HTTP streaming response uses one of the following representations. The server selects the representation with HTTP content negotiation.

A server MUST support JSON Sequence. The other representations are optional.

Media type Representation Requirement
application/json-seq JSON Sequence required
application/x-ndjson, application/jsonl NDJSON/JSONL optional
application/cbor-seq CBOR Sequence optional
application/x-jelly-rdf RDF representations optional

An HTTP streaming subscription response MAY include an Accept response header that lists the media types supported by the outbox.

RDF representations MUST follow the RDF isomorphism requirement in the LWS Profile section of [[!LWS10-CORE]].

RDF representations can refer to RDF Messages [[?RSP-MESSAGES]].

JSON Sequence

Each notification is a JSON text in an RFC 7464 JSON Text Sequence [[!RFC7464]]. The server writes one RS byte, 0x1e, then one compact JSON object encoded as UTF-8, then one LF byte, 0x0a. The response body contains no byte order mark and no blank line.

NDJSON/JSONL

NDJSON/JSONL uses application/x-ndjson for NDJSON [[?NDJSON]] and application/jsonl for JSONL [[?JSONL]]. Both use the same framing. Each notification is a compact JSON object encoded as UTF-8 and terminated by one LF byte, 0x0a. The response body contains no byte order mark, no blank line, and no trailing partial line.

CBOR Sequence

Each notification is one complete CBOR item. Items are written back-to-back. The sequence has no delimiter, length prefix, enclosing array, or self-described CBOR tag. The result is an RFC 8742 CBOR Sequence [[?RFC8742]].

Each item is a plain CBOR object or a CBOR-LD item. See [[?CBOR-LD-10]].

application/ld+cbor-seq may be needed.

Jelly-RDF

Section 6.4 of [[JELLY-RDF]] defines this variant. Each notification is one RdfStreamFrame Protobuf message. Each frame is preceded by a Protobuf varint containing its length in bytes. The stream has no newline delimiter and no gRPC message envelope.

Content Negotiation

The subscriber selects a representation with the Accept request header using HTTP content negotiation [[!RFC9110]]. The server MUST select one of the supported media types listed in . Standard HTTP quality values and media ranges apply.

A request with no Accept header, or an empty Accept header, selects application/json-seq. When more than one representation is equally acceptable, the server selects application/json-seq. If no supported representation is acceptable, the server MUST return 406 Not Acceptable.

Subscription Type Identifier

An HTTP streaming subscription MUST use the HttpStreamingSubscription string as its subscription type when interacting with the NotificationService.
